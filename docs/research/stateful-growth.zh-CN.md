# 剪枝驱动的状态式生长实现方案

日期：2026-09-17。状态：研究与实现设计，尚未修改应用代码。

## 1. 目标与结论

把“播放一棵预先生成的树”改成“依据当前活枝、空缺、树形约束和生长资源，决定下一次长什么”。剪枝不仅减少枝条，还会改变后续生长位置和方向，形成「观察 → 修剪 → 萌芽 → 选择保留 → 再修剪」的循环。

这里将需求中的“指导归 0”按“枝条最终归零、没有可继续剪的目标”理解。当前正式剪枝链路未发现对应的指导评分系统，本方案不新增评分。

推荐采用**保留主干骨架与树形规则，侧枝使用状态驱动的增量生成，并为每个有效局部层级提供确定性的恢复保障**。第一版保留现有整根旁支修剪方式，后续再开放细枝修剪；不要同时重做全部树形、交互和生长引擎。

## 2. 现状研究

研究基于当前工作区（含已有未提交修改）；已 fetch，当前 HEAD 与 origin/dev 无提交差异。下列设计应在落地时重新核对其他任务已修改的形态模块。

| 位置 | 当前机制 | 对体验的限制 |
| --- | --- | --- |
| `prototype/growth.mjs` 的 `grow/snapshot` | 每次先 `generate(config)` 生成完整树，再按全局进度展开，最后应用剪枝及补枝 | 正常成长的拓扑已经确定；成熟进度封顶后不再产生新结构 |
| `prototype/regrowth.mjs` 的 `regrowthPlan` | 原始 `primary` 变成固定槽位；低于原数一半（向上取整、至少 2 且不超过槽位总数）才补充 | 全树够数时，即使某个局部已经剪空也不会补 |
| 同文件 `appendRegrowth` | 复制原枝整个家族，调整角度、长度、着生位置 | 新编号不等于新结构，仍复用旧拓扑 |
| `prototype/pruning-model.mjs` 与 `server.mjs` | 只允许剪 `primary`，整族删除；主干受保护 | 目前不能把“层级”直接当作所有枝序都能剪 |
| `tests/regrowth.test.mjs` | 已覆盖全剪恢复、多代再剪、确定性和服务器保存 | “完全没有恢复”不是当前源码的准确描述；现有 4–8 小时等待也可能让用户误以为不会再长 |
| `prototype/cheats.mjs` | 作弊保存最多 64 条剪枝记录，部分原始枝 ID 走预生成集合校验 | 新模型需统一按当时活树校验，长时间反复修剪需调整历史容量方案 |

`prototype/core/v1/model.mjs` 中已有独立芽竞争实验：根据空间、光照和方向选择候选生长方向。可借鉴评分思想，但它具有固定槽位、深度和实验时长约束，不应直接替换正式应用，也不修改冻结的 `core/v1`。

## 3. 算法选择

[Self-organizing tree models for image synthesis（2009）](https://algorithmicbotany.org/papers/selforg.sig2009.html)以芽和枝对光照、空间的竞争及内部调节形成树形，并支持修剪等交互。适合借鉴“先读取当前环境，再决定芽的命运”的原则。

[Modeling Trees with a Space Colonization Algorithm（2007）](https://algorithmicbotany.org/papers/colonization.egwnp2007.html)提供空间驱动的枝系生成方法。可借鉴空缺区域对生长方向的影响，但本项目第一版无需引入完整三维吸引点系统。

以下是针对本项目的工程设计，并非论文算法复现，也不宣称植物生理仿真：使用二维候选芽、局部空缺评分、树形限制和数量保障。随机性负责自然差异；恢复保障由确定规则承担，不能只靠抽到新芽。

## 4. “层级”分成两种维度

1. **枝序 `order`**：主干为 0，一级侧枝为 1，二级侧枝为 2……它描述结构关系。`role` 继续用于绘制及交互，不能直接代替枝序；现有 `bough`、连续干段和设计稿里的 `branchOrder` 需要适配规则。
2. **生长区域 `zoneId`**：沿主干弧长划分的有效冠区，可附带侧向范围。它描述哪里缺枝。悬崖式沿弯曲干线划分，不能统一按屏幕高度切成三层。

一级枝按“冠区”计数，二级及以下按“仍活着的父枝”计数。不能只统计全树同一枝序总数，否则一侧茂密会掩盖另一侧缺失。

区域是可生长范围，不是固定枝位：新枝可以在范围内选择新的着生点，不能绑定被剪枝的原位置。文人树裸干、风吹式迎风留白等区域明确禁止自动填满；这些是树形规则，不是缺枝。

父枝被剪后，其下的局部恢复任务一起取消。先在存活祖先上恢复上一级，新枝成熟后才获得自己的下一级生长任务，避免在空气中生出子枝。

## 5. 生长规则与恢复保障

### 5.1 每个局部维持数量区间

为每个有效区域/父枝计算 `low`、`target`、`high`：低于 low 启动恢复，补到 target 后结束，高于 high 不再分叉。阈值依据树形、父枝长度及粗细、成熟度、允许空间计算，不能由原始枝条总数直接推导。

原型可先试：普通成熟冠区 low=1、target=2、high=3；成熟侧枝的直接子枝 low=1、target=2、high=3。文人树允许 target=1，最末枝序不要求继续分叉。以上仅为调参起点，不是统一配置。

分别记录活枝数、已安排的新芽数和可剪枝数。安排中的芽占用容量以免重复补充，但只有真正形成可剪枝后才算“玩法恢复”；失败或父枝死亡的芽释放配额并重排。

### 5.2 从当前状态产生一个新生长单元

每次决策按以下顺序执行：

1. 更新当前活枝、局部成熟度、空缺和正在恢复的任务。
2. 从活父枝可用区间采样候选芽点，读取父枝切线、附近枝叶占用、最近剪口和树形方向。
3. 先排除穿过主干、盆器、禁止冠区或越过画框的候选，再评分。
4. 评分综合缺枝程度、可用空间、方向/光照、父枝承载能力、切口附近暂时抑制，并加入小幅稳定随机扰动。
5. 选择候选，只创建当前新芽/枝段；它的后代必须在未来读取当时状态再决定。不得一次递归生成完整后代模板。
6. 消耗当前周期的生长额度；预算有限时优先修复最久未满足的局部，再安排普通延伸，防止弱势层级一直等不到资源。

可表达为 `nextState = advance(currentState, events, targetTime, rules)`。相同状态与事件产生相同结果；不同剪法改变占用与候选选择，因此得到不同未来。

已有成熟木质枝段保留几何，新增部分逐渐伸长、变粗、长叶。幼枝每长完一小段才决定下一段方向，避免每帧重新布局造成树干跳动。区分“逻辑枝条”与“渲染曲线段”，连续延长不能错误增加枝序或可剪数量。

### 5.3 不会永久剪空的保障

- 主干与有效生长支撑不可被剪掉；即使叶片和一级枝都归零，也保留基础恢复额度，不以现有叶量作为唯一能源。
- 每个有效缺枝局部都建立有截止时间的恢复任务。普通评分找不到芽点时，扩大该区域候选采样、缩短新枝长度，再使用区域内预留的安全生长通道。
- 安全通道是范围约束，不是完整枝系模板；剪掉原枝后不复活旧 ID，也不恢复旧子树。
- 达到活跃节点预算时，优先取消未出生的普通生长计划并压缩等价渲染段，保留恢复配额；不得为了空出容量偷偷删除用户保留的成熟枝。
- 配置必须满足有效区域的最低需求总量不超过预算，且每个必保区域有可达通道。开发校验不通过时拒绝该配置，不能把“稍后重试”当作无限等待的兜底。

保障条件是：用户停止继续剪、仍有受保护主干且配置有效时，缺枝区域在有界时间内恢复出可剪枝。持续剪掉每一个刚形成的枝条时，不承诺每一帧都存在可剪目标。

### 5.4 节奏建议

首轮实验参数：剪后立即登记恢复任务并显示轻微芽点提示；10–30 分钟出现实际新芽，2–6 小时长出短枝，12–24 小时形成可剪枝，24–48 小时逐步补叶。达到基本数量后转为更慢的正常生长。

这些是交互体验参数，非真实树木时间。需在设计系统加快进预览后比较是否合适。新芽阶段暂不允许剪，达到长度与成熟度门槛才显示剪枝点；服务端使用相同规则。

浇水只加快浇水之后的生长，不能修改过去枝条身份或形态。维持免费基础恢复，不强迫用户浇水才能救回剪空的树。沿用主干保护、落枝反馈和无伤疤的现有视觉约定。

## 6. 状态、时间与存储

### 6.1 最小状态

```text
GrowthState
  engineVersion, rulesVersion, simulatedAt, nextEventIndex
  branches[]: id, parentId, order, zoneId, attachment,
              bornAt, phase, geometrySegments, vigor, nextBudOrdinal
  buds[]: id, parentId, attachment, readyAt, status
  recoveryJobs[]: scopeId, startedAt, deadline, target
  zones[], growthBudget, biologicalClock
```

叶簇由活末梢及其局部年龄生成，保存稳定 key；不能再复制原枝的叶簇家族。所有父子关系、枝 ID、叶簇引用在状态更新后校验。

新 ID 使用版本前缀加稳定出生序号；随机键基于树种子、引擎版本、父枝 ID、芽序号和用途。先排序候选再打破平局，不使用 `Math.random()`、当前渲染次数、请求 UUID 或数组偶然顺序。剪枝 UUID 仅用于请求幂等。

### 6.2 确定性演进

采用固定逻辑时间格（例如 10 分钟）结合离散事件。刷新频率不影响决策次数；两次刷新和一次离线补算到同一时间应得到相同状态。视觉可在已确定的生长段之间插值。

剪枝和浇水按服务器时间及全局事件序号排序。推进至事件前状态 → 验证并应用同刻用户事件 → 处理同刻生长决策；同毫秒多事件按序号处理。新剪枝不反写过去；所有新生长只能读取此前已发生的事件。

引擎输入显式传入时间，不内部调用当前时钟。天气外观不参与核心生长决策；如果以后参与，需要先保存可回放的环境事件。

### 6.3 长期运行与接口

以“初始化基线 + 用户事件日志 + 可再生检查点”重建当前树。第一阶段先实现纯重放正确性，再添加检查点；检查点不是新的生长规则。

检查点记录规则版本、处理到的事件序号与时间。回看过去要选过去的检查点；作弊回退或改种子应使受影响检查点失效。无新增结构、无待处理事件时跳到下一决策时间，不能逐分钟空跑一百年。

活节点、最大枝序、单次补算量都有预算。首版不做自动死亡换枝：达到稳定冠幅后暂停普通增枝，剪枝腾出空间后恢复，因此不会无上限膨胀。历史事件可持续增长，应分页/分段保存和压缩检查点，不能简单删掉过去剪枝。

`server.mjs` 的树详情及 Gallery 当前显式挑选返回字段，必须补齐版本/基线/检查点等必要数据；缩略图、分享图、回放、设计系统、作弊模式都走统一版本路由。仅修改 growth.mjs 会造成页面之间状态不一致。

服务端仍在存储事务中推进当前树、校验目标活着且可剪、保存事件与 revision；同一 UUID 重试只生效一次。两个用户同时剪同一枝，仅一个成功；不同枝的有效剪枝按提交顺序应用。客户端显示旧目标收到冲突后刷新。

本地 JSON 和 PostgreSQL 都要验证状态序列化与迁移；本地存储测试不代表已验证真实 Neon。

## 7. 兼容与分阶段落地

**阶段 A：引擎和可视原型。** 新建 `growth-state.mjs`、`growth-rules.mjs`、`growth-engine.mjs`，按现有渲染数据结构输出曲线和叶簇。先做真柏、文人、扫帚三种差异明显的树形，设计系统展示同一初始树不同剪法以及全剪后的时间序列。正式剪枝仍只支持 primary。

**阶段 B：接入完整应用。** 通过 `growth.mjs` 按版本分发新旧引擎，统一 `canPrune`；更新 pruning-model、服务端、回放、Gallery、分享、作弊和存储接口。新树只预置种子/幼树与主干规则，侧枝从出生起增量生成，避免新树仍完整播放旧模板。

**阶段 C：已有树迁移。** 先为旧版本保留现有行为，不静默改写历史。迁移时以切换时刻的旧树完整可见状态为基线，保留存活 ID、几何、已有剪枝记录，将未来生长切换到新引擎；切换前历史仍走旧引擎。通过快照对比确认迁移当帧没有外观跳变。再推广全部七种树形。

**阶段 D：细枝玩法。** 在局部恢复与移动端选择稳定后再开放二级枝；使用放大/局部选择避免提示点拥挤。此时同步扩展服务端许可，不只放开前端命中。整枝剪除与截短是不同交互，截短留桩另立需求。

顺序上先证明“新生后代确实依据当前状态决定”和“局部缺枝可恢复”，再优化材质、颜色与动画。现有尚未合入的 branch-design、crown 等研究模块不作为隐式前提。

## 8. 验收与测试

| 场景 | 必须观察/验证的结果 |
| --- | --- |
| 全树尚有很多枝，只剪空一个有效冠区 | 该区独立建立恢复任务并长出新枝 |
| 剪空全部可剪旁支，不浇水 | 受保护主干留存；在配置规定时限内重新出现可剪枝 |
| 同一初始树剪左侧 vs 剪右侧 | 后续位置/方向有可解释差异，未剪成熟枝不移动 |
| 连续 100 轮剪掉恢复枝 | ID 不复用、没有永久死局；作弊保存不受旧 64 条限制破坏 |
| 父枝与待出生子芽同时存在时剪父枝 | 所有子芽/任务取消，无悬空枝或旧枝复活 |
| 新芽数已足但仍未可剪 | 不重复超额补芽，也不能提前报告恢复完成 |
| 刷新、不同补算分段、离线多日、回放同一时刻 | 相同版本和事件得到一致拓扑、身份及几何 |
| 加入未来剪枝、改变请求 UUID | 不改变过去快照 |
| 迁移、作弊回退/换种子、服务重启 | 不丢事件、不误用检查点；迁移切换帧保持外观 |
| 空间紧张、预算达到上限、全部候选低分 | 必保区域仍有确定恢复路径，不无限重试 |
| 七种树形及小屏幕 | 裸干和留白得到保留，新枝连接自然、无穿盆/断裂/画面跳动 |
| 长期成熟且不修剪 | 枝条数量趋于稳定，无无限细分及持续离线计算 |

验证使用 Node.js 24，应用改动后运行 `npm test`，并做桌面/手机浏览器视觉验收。先测当前 snapshot 的耗时作为基线，再制定节点预算和性能门槛；普通单树交互不应等待长时间历史重放，Gallery 需专门测多树批量情况。

产品侧观察恢复到第一根可剪枝所需时间、缺枝任务超时数、连续修剪轮数、用户是否保留新枝及下一次回访情况。优先通过快进对比审阅参数，再决定是否调整真实等待时间。

最终验收标准：**剪枝改变未来的生成决策；有效局部剪稀后有界恢复；树形和用户保留的结构不被全树重建抹掉；同一历史在所有入口一致。**
