# 新版盆栽设计系统应用接入方案

状态：待 review 的实施方案。本文不切换应用、不修改已有盆栽、不涉及推送或部署。

## 推荐范围

新认养盆栽采用已审阅的七种树形、五套通用配色、相容冠型与叶形，以及受控随机枝干、固定层次上色和成熟枝梢补冠。保留首页一键认养、浇水、剪枝、回放、小院与分享流程，不把设计系统的参数面板搬进普通用户页面。

首版继续使用应用现有的时间、生长、浇水和剪后再生机制。`adaptive-growth-model.mjs` 是另一个状态式生长实验，不与此次视觉接入一起切换。视觉算法与生长规则分开验收，避免同时改变树的样子和养护行为。

老树保留原有生成身份和历史记录；不把相同种子直接交给新算法重画，因为新版的分枝数量和 ID 已不同，旧剪枝记录不能直接对应。以后若需要“旧树换新版”，单独设计为可预览的新树副本，不能默认覆盖原树。

## 当前代码与接入缺口

| 环节 | 当前入口 | 接入时必须解决的差异 |
| --- | --- | --- |
| 认养配置 | `prototype/claim.mjs`、`server.mjs` | 浏览器和服务器由认养 ID 推导同株；目前只生成旧树形/外观组合 |
| 成熟骨架 | `prototype/bonsai-language.mjs`、`bonsai-individual.mjs` | 已有新版算法，但仍依赖多个研究模块，不能把可变实验文件当作永久存档算法 |
| 生长与存档 | `prototype/growth.mjs` | `record.version` 被保存，但 `snapshot`/`grow` 默认没有按记录版本选择算法；仅修改 `VERSION` 不够 |
| 应用画面 | `prototype/mvp.mjs` | 普通绘制和浇水绘制都写死了 viewBox；新版极端树形需要完整构图 |
| 色彩与天气 | `prototype/color-system.mjs`、`growing-render.mjs` | 现有四级叶色与新版三组四级叶色不同，新版 `layerPalette` 也不会自动接受旧 CSS 叶色调整 |
| 盆器 | `claim.mjs`、`bonsai-language.mjs` | 应用保存随机盆器，设计页按树形指定盆器；接入时必须以存档盆器为准 |
| 剪枝与再生 | `pruning-model.mjs`、`regrowth.mjs`、服务端 cuts API | 继续按 primary 枝族修剪；新 ID 必须贯穿客户端命中、服务器校验和历史回放 |
| 调试保存 | `prototype/cheats.mjs`、`mvp.mjs` | 旧 normalize/look 逻辑可能丢失新版选项；重建校验记录时也要保留版本 |
| 小院与分享 | `gallery.mjs`、`share-preview.mjs` | 与主页面使用同一个版本路由，不能只替换首页的绘图函数 |

## 1. 冻结算法与记录身份

建议新增版本 `bonsai-growth-3`，表示这一组确定的生成、配色和生长规则。通过统一入口按 `record.version` 选择完整实现。旧 `bonsai-growth-2` 和已确认的无版本旧记录仍走旧实现；未知版本明确报错，不能静默改成新树。

将审核通过的纯生成、参数目录与必要依赖整理进一个冻结的版本目录，例如 `prototype/core/v3/`。设计页也调用同一实现作为“应用版”基准，下一轮实验使用另一个候选入口。不能只冻结 `bonsai-language.mjs`，却继续引用会被实验改写的 morphology、trunk、branch 和 crown 模块。旧版冻结基准需与实际已发布版本核对，不能把共享工作区中的实验改动误认为老树标准。

建议继续沿用现有 document 结构，将新版参数显式保存：

```json
{
  "version": "bonsai-growth-3",
  "config": {
    "seed": "稳定的个体种子",
    "preset": "juniper",
    "crown": "cloud",
    "leaf": "scale",
    "palette": "mist",
    "variation": 0.55,
    "density": 0.5,
    "pot": "沿用现有规范化盆器对象"
  }
}
```

示例中的 pot 是说明性占位；实际继续存现有对象。保留 `createdAt`、`cuts`、`waterings`、`revision` 及访问活动字段，不改写历史。`revision` 只处理并发，不承担算法版本职责。数据库当前保存 JSON/JSONB 文档，预计不需要新增表或批量改写旧记录，但要补齐读写往返验证。

同版本、同配置、同时间和同操作历史必须重建同一棵树。未来改变随机采样、枝条 ID 或几何含义时另建版本。版本路由应被浏览器与服务器共用，避免互相导入生长入口造成循环依赖。

## 2. 新认养：保存用户实际看到的那一株

扩展 `configForClaim` 为按明确版本生成配置。稳定种子分别抽取树形、配色、相容冠型/叶形、盆器及个体参数；各维度使用独立随机键，五套配色对所有树形开放。

建议首版以“自然变化、均衡枝量”为主要分布，少量抽到克制/鲜明和疏朗/丰茂，使用设计页已经验证的范围。各方案权重写成可审阅配置，不在多个入口各写一份概率。参数抽取后完整入档，后续发布调整权重不会改变已认养树。

首页候选带上明确的生成版本。认养请求提交候选 ID 和该版本，服务端按受支持版本重新推导配置，不信任任意客户端几何。发布切换时，已经打开的旧首页仍能认养所见旧候选；新首页获得新版本。重试沿用同一 ID，已有记录直接返回，不重新抽样。

应用正常认养继续使用随机保存的盆器；设计页的树形默认盆器只作缺省值，不能覆盖认养记录。认养前后可以有自然时间推进，但树形、种子、叶色和盆器必须一致。

## 3. 生长、剪枝与补冠共用一个版本入口

推荐链路：

```text
记录版本 → 对应成熟生成器 → 时间/浇水生长 → 剪枝历史与再生 → 渲染
```

当前 `grow` 已支持注入 generator，可作为接入点；正式应用让版本路由统一决定它，不要求每个调用方自行传函数。所有临时重建记录，包括 cheats 校验历史，也必须带上版本。

- 保留主干逐段伸长增粗、顶部新枝较短且分叉较少的表现，以及当前浇水和回放节奏。
- 保留现有 primary 枝族剪枝粒度，不在此次扩展成任意细枝可剪。稳定 ID 用于前后端同一时刻的校验，剪枝后幸存枝条不重新随机。
- 成熟枝梢补冠只在初始成熟骨架生成阶段执行，补充冠依附对应枝条；剪除枝条时一并移除，不能在剪后覆盖检查中立即补回。
- 再生枝继续经历等待、伸展和展叶，并继承所属枝族的叶形、色组及补冠定义；再生不应恢复成旧版平面叶团。
- 覆盖幼苗、成树、连续剪枝、剪后再生、重剪再生枝、浇水恢复和离线回放。不要以静态成树好看替代生命周期验收。

## 4. 把色组、天气和构图一起接入

**颜色。** 新版以 palette 为树冠颜色的唯一来源，旧 appearance/look 继续服务旧版本。定义前、中、后三组各四级的材质接口；天气/昼夜对整套色组施加同一套有限修色，保留组间层次和冠内体积。先验证白天与设计页一致，再检查黄昏、夜间与阴雨；不能让旧四叶色覆盖三组固定配色。背景、树皮与盆器仍使用现有环境体系，按新版选项明确映射，不隐式把旧 look 同时当作叶形和叶色。

**构图。** 成熟构图由完整树冠和盆器边界计算，并在同株成长、剪枝时保持稳定；合并保留应用土面和工具的安全空间。不要每帧按现存叶量重新缩放，也不要把设计页的自由居中直接搬进应用，导致盆器悬空或压住剪刀、浇水壶。统一主页面、浇水重绘和回放的取景入口，专门检查悬崖式和风吹式；分享图可以保留适应横版的独立构图，但必须使用相同的树模型。

**交互与性能。** 保留 wind、pruning、watering 所需的 SVG 节点属性和父子关系，验证新叶团参与风动与水滴碰撞。新版补冠和多组渐变会增加节点量，应测量手机绘制、小院滚动和服务端 PNG 开销。必要时按版本与完整配置缓存只读成熟骨架，每次生长使用副本；不能复用会被 grow 修改的对象，也不能为了性能直接删掉枝梢的唯一树冠。

## 5. 实施顺序和交付门槛

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| A：冻结与兼容 | 冻结已审阅算法、建立版本路由、固定新记录结构，默认认养仍保持现状 | 旧记录在相同时间的几何、配色、盆器和剪枝回放与既定基准一致 |
| B：完整应用预览 | 在本地应用接入新版候选、认养、保存、浇水、剪枝、再生、调试、小院、分享 | 同株跨页面一致，重开链接可复现；七种树形全生命周期不缺冠、不漂冠、不裁切 |
| C：视觉与性能 review | 真实手机尺度、昼夜天气、稀密和变化幅度极值；与设计页固定种子对照 | 固定色组层次、枝线和冠体积保持；工具可操作，性能实测满足交互要求 |
| D：默认认养切换 | 审阅通过后，新候选默认用新版；旧候选和旧记录仍可读写 | API 重试、旧页面跨发布认养、新旧混合小院与分享全部通过 |

发布前运行完整 `npm test`，并做浏览器视觉检查。API 集成测试须覆盖新旧版本创建、重复认养、切换期间旧候选、剪枝/浇水/cheats，以及分享 PNG；旧记录基准需包含已有剪枝与再生历史。现有本地 JSON 测试不代表真实 Neon 与部署验证。

回退开关只停止创建新版候选，不移除已创建新版盆栽的读取和操作能力。若回滚到不认识新版记录的旧服务代码，会让新树无法使用，因此首个兼容版本应先具备双版本读取，再启用新版创建。

每阶段先交付本地差异和可操作预览供 review；得到本次明确 push 许可后，才按仓库 dev → CI → main 流程发布。只有检查实际部署状态后才宣称上线。

## 首轮建议的验收样本

七种树形各保留至少一个固定成树样本和同株幼苗/中期/成熟对照；另保留粗细过渡、缺冠问题的两个回归种子：`4bc5f0b6-03be-445a-a1cb-b5268a052c03`、`655bc0bf-ed33-4435-bbf6-e27eafaff27a`。对同一株依次检查设计页、应用预览、认养重开、小院和分享图。颜色允许因环境有受控变化，几何身份必须一致。
